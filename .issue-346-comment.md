My preference is to honor `.gitignore` whenever `respect-gitignore = true`, regardless of whether Git metadata is present.

I would define the behavior as follows:

| `respect-gitignore` | Git metadata | Behavior |
|---|---|---|
| `false` | present or absent | Do not read `.gitignore` files |
| `true` | present | Apply `.gitignore` files, using the repository root as the parent-search boundary |
| `true` | absent | Apply `.gitignore` files, using the logical lint/project root as the parent-search boundary |

Here, Git metadata should include both a `.git` directory and a `.git` file, as used by worktrees and submodules.

The main reason is that mado has an explicit option whose documented meaning is currently "Exclude files that are ignored by .gitignore." The option defaults to `true`, and this repository explicitly sets it to `true` while placing `target/` in `.gitignore`. Requiring an undocumented `.git` precondition makes the effective lint input depend on how the same source tree was transported: a clone, source archive, or Docker context can produce different results. For a linter, I think reproducibility should take precedence over matching the default behavior of a general-purpose filesystem search tool.

The packaging case in #141 also looks like a normal use case rather than a producer error. Source archives normally omit `.git`, and `.dockerignore` controls what enters a build context; it does not define what mado should walk after files have been copied into an image.

The rg and ruff precedent still matters, but their role is different. In particular, rg searches arbitrary filesystem locations, where applying unrelated ancestor ignore files is a significant concern. mado already has a project configuration value that explicitly asks it to respect `.gitignore`.

There is one important implementation constraint: calling `require_git(false)` alone is too broad. The `ignore` crate documents that this can read `.gitignore` files from parent directories above a repository boundary. When no repository exists, mado should establish its own logical boundary instead of allowing a user or host-level ancestor `.gitignore` to change the lint result.

I would not add a separate public `require-git` boolean yet. It exposes a dependency-level distinction and creates confusing combinations with `respect-gitignore`. The suggestion to honor `.gitignore` only when the current boolean was explicitly written would also require tracking configuration provenance: explicit `true` and default `true` are currently the same effective configuration, and I do not think they should behave differently. If a real compatibility use case appears later, a single policy such as `always` / `repository-only` / `never` would be clearer than two interacting booleans.

The follow-up implementation should at least test:

- the same tree with and without Git metadata;
- `respect-gitignore = false`;
- an ancestor `.gitignore` above the logical root;
- nested `.gitignore` files;
- both `.git` directory and `.git` file markers.

It would also be worth explicitly deciding whether Git global ignores and `.git/info/exclude` are part of this option. `WalkBuilder` controls those separately, so leaving their behavior inherited from defaults risks creating another undocumented dependency-level contract.
